Optimizing SQL Queries
====================================================

Your database is the **keystone** of your application architecture.
Extracting performance from it provides substantial benefit everywhere
else in the system. Today we focus specifically on **query
optimization** -- the easiest, least expensive, and most generally
applicable performance lever.

Today's arc:

- **Read the plan first**, optimize second.
- Understand basic query plans, then unwind advanced plans inside-out.
- See how small SQL changes can materially change the plan (join key
  selection, Memoize).
- Use IO, memory, and serialization flags to diagnose resource
  bottlenecks.
- Decide when to add **indexes** and when not to (SARGABLE queries).
- Pick the right **join strategy** (nested loop, merge, hash).

.. admonition:: Key Insight
   :class: tip

   In the "rules of perf" poster style: **(1) don't do it, (2) cache
   it, (3) batch it, (4) pipeline it, (5) don't do it in Python**.
   Query optimization is mostly a mix of rules 1 and 2 -- stop asking
   the database to do work it does not need to do, and make the work
   it does do reusable.


1 -- Why This Topic Matters
====================================================


Query Optimization as a Performance Lever
----------------------------------------------------

We are focusing on **query optimization**, specifically, because:

- It applies to **most workloads** -- there is almost always a slow
  query worth fixing.
- It is the **easiest and least expensive** mechanism for improving
  performance. No new hardware, no schema migration, no application
  rewrite.
- The technique is **mechanical** and separable from modeling choices.
- Improvements here **amplify every other optimization** you may
  eventually reach for.


General Advice Before You Tune Queries
----------------------------------------------------

Past query optimization, other levers exist -- tackle them roughly in
this order:

- **Hardware optimization**: use tools like ``htop`` and ``iotop`` to
  diagnose CPU, memory, and disk-IO starvation on active servers.
- **Application optimization**: make sure your application only hits
  the database when it absolutely needs to. Cache prior results,
  aggregate metrics, batch reads and writes.
- **Database design and schema**: design tables, relationships, and
  types to support your real access patterns. Consider deliberate
  denormalization for hot read paths. Pick the most appropriate
  datatype for each column.
- **Hardware and system tuning**: enough CPU / RAM / disk IO, server
  parameters (buffer pool, connection limits), fast storage (SSDs),
  reliable network.
- **Monitoring and tuning**: measure query response times, transaction
  throughput, resource utilization; design for scale on the assumption
  that you will be successful.

All of this matters -- but it is usually cheaper to fix a hot query
than to rent more RAM.


Query Optimization Guidelines
----------------------------------------------------

A compact playbook for writing faster SQL:

- **Reduce data returned**: project only the columns you need.
  ``SELECT *`` is a code smell.
- **Avoid full table scans**: ensure queries can use indexes; combine
  with an efficient ``WHERE`` clause.
- **Filter early**: the earlier a predicate eliminates rows, the less
  work every downstream step does.
- **Index thoughtfully**: create indexes on frequently queried
  columns and on columns used for sort / group operations -- but do
  not over-index.
- **Use appropriate JOIN types**: choose ``INNER`` / ``LEFT`` /
  ``RIGHT`` based on semantics, not habit, and be aware that the
  physical strategy (nested loop / merge / hash) is chosen by the
  planner.

These are rules of thumb. To apply them, you must first **see** how the
database is executing the query. That means starting with the query
plan.


2 -- Query Plans
====================================================


What Is a Query Plan?
----------------------------------------------------

A **query plan** is a blueprint generated by the database's **query
optimizer**, which analyzes the SQL statement and determines the most
efficient way to retrieve the data.

A plan describes:

- The **order of operations**.
- The **tables to access** and in what order.
- The **join strategies** (nested loop / merge / hash).
- The **indexes** used (or not used).
- Estimated **costs** and **row counts** for each step.

Candidate plans are evaluated by the planner, and the cheapest is
picked. Humans read the plan to develop intuition about what to
optimize.

.. admonition:: Key Insight
   :class: tip

   The best way to optimize a SQL query is to ask the engine to do the
   **minimal amount of work possible**. The query plan is the X-ray
   that shows you where the work is going.


Generating Query Plans: ``EXPLAIN`` and ``EXPLAIN ANALYZE``
-----------------------------------------------------------

PostgreSQL exposes plans through two commands:

- ``EXPLAIN`` prints the planner's **estimates** -- it does **not**
  execute the query.
- ``EXPLAIN ANALYZE`` **actually executes** the query and prints both
  the estimates and the **measured** runtime numbers.

.. code-block:: sql

   EXPLAIN
   SELECT * FROM employees WHERE age > 30;

Estimates only:

.. code-block:: text

                                  QUERY PLAN
   -----------------------------------------------------------------
    Seq Scan on employees  (cost=0.00..22.50 rows=791 width=39)
      Filter: (age > 30)
   (2 rows)

.. code-block:: sql

   EXPLAIN ANALYZE
   SELECT * FROM employees WHERE age > 30;

Estimates plus actual execution numbers:

.. code-block:: text

                                           QUERY PLAN
   -----------------------------------------------------------------------------------------------
    Seq Scan on employees  (cost=0.00..22.50 rows=791 width=39) (actual time=0.053..0.404 rows=791 loops=1)
      Filter: (age > 30)
      Rows Removed by Filter: 209
    Planning Time: 0.146 ms
    Execution Time: 0.506 ms
   (5 rows)

- **Use ``EXPLAIN ANALYZE`` for read queries**. The extra information
  is worth the cost of running the query.
- **For write queries, wrap in a transaction that you roll back**, so
  the diagnosis does not leave state behind:

  .. code-block:: sql

     BEGIN;
     EXPLAIN ANALYZE
     UPDATE employees SET salary = salary + 1000 WHERE id = 7;
     ROLLBACK;


A Brief Interlude: Transactions
====================================================

``EXPLAIN ANALYZE`` actually executes your query. For anything that
mutates state, you must run it inside a transaction you will throw
away.


What Is a Transaction?
----------------------------------------------------

- A **transaction** is a sequence of one or more SQL statements
  executed as a single unit.
- Statements can be mutating (``INSERT``, ``UPDATE``, ``DELETE``) or
  read-only.
- During a transaction, all changes either **succeed together** or
  **fail together**.
- On error, a rollback ensures that **no partial changes are saved**.


ACID, Briefly
----------------------------------------------------

SQL databases adhere to the **ACID** transaction model:

- **Atomicity**: all sub-statements succeed, or the whole transaction
  rolls back.
- **Consistency**: transactions only move the database from one valid
  state to another.
- **Isolation**: concurrent transactions are isolated from each other,
  preventing data races.
- **Durability**: once a transaction commits, changes survive even a
  system failure.

Transaction control commands:

.. code-block:: sql

   BEGIN TRANSACTION;   -- starts a transaction
   COMMIT;              -- saves all changes
   ROLLBACK;            -- undoes all changes since BEGIN
   SAVEPOINT name;      -- marks a sub-point you can roll back to

A typical diagnostic pattern:

.. code-block:: sql

   BEGIN TRANSACTION;

   -- Give employee 7 a raise
   UPDATE employees SET salary = salary + 1000 WHERE id = 7;

   -- And dock employee 8 to balance the budget
   UPDATE employees SET salary = salary - 1000 WHERE id = '8';

   -- Commit if both operations succeeded
   COMMIT;

If any single statement errors out inside the transaction, PostgreSQL
**automatically** puts the transaction into a failed state; subsequent
statements are ignored until you issue ``ROLLBACK``. You do **not** get
a partial update.


Best Practices for Performance
----------------------------------------------------

Transactions are powerful but come with real costs:

- **Break up long-running transactions** -- they hold locks and reduce
  concurrency.
- **Optimize sub-queries within a transaction** to keep it short.
- **Commit as soon as the unit of work is complete** to release
  resource locks.

Now, back to query plans.


3 -- Reading Basic Query Plans
====================================================


Anatomy of a Plan Line
----------------------------------------------------

Take the same ``EXPLAIN ANALYZE`` output as before:

.. code-block:: text

                                           QUERY PLAN
   -----------------------------------------------------------------------------------------------
    Seq Scan on employees  (cost=0.00..20.50 rows=762 width=27) (actual time=0.111..0.344 rows=762 loops=1)
      Filter: (age > 30)
      Rows Removed by Filter: 238
    Planning Time: 0.128 ms
    Execution Time: 0.405 ms
   (5 rows)

Read it field by field:

1. **Seq Scan on employees** -- the database performs a sequential
   scan on the ``employees`` table, reading every row to check the
   filter condition.
2. **cost=0.00..20.50** -- the planner's cost estimate. ``0.00`` is
   the start-up cost; ``20.50`` is the total cost to complete.
3. **rows=762** -- estimated number of rows produced by this step.
4. **width=27** -- estimated average size (bytes) of each row returned.
5. **actual time=0.111..0.344** -- measured start-up and total time in
   milliseconds.
6. **actual rows=762, loops=1** -- measured rows and how many times the
   step executed.
7. **Filter: (age > 30)** -- the predicate applied.
8. **Rows Removed by Filter: 238** -- how many rows the scan examined
   but discarded.
9. **Planning Time: 0.128 ms** -- time to generate the plan.
10. **Execution Time: 0.405 ms** -- time to execute it.

You can already see the importance of **selecting only what you need**
and **filtering early**: every extra row the plan carries forward costs
you CPU, memory, and IO.


Query Plan Costs Are Relative, Not Absolute
----------------------------------------------------

An important disclaimer straight from the PostgreSQL docs:

    Unfortunately, there is no well-defined method for determining
    ideal values for the cost variables. They are best treated as
    averages over the entire mix of queries that a particular
    installation will receive. This means that changing them on the
    basis of just a few experiments is very risky.

Costs are **relative measures**, not absolute times. They help you:

- Compare different steps of the same plan.
- Compare two candidate plans for the same query.
- Spot the most expensive step to focus your optimization efforts.


PostgreSQL Cost Constants
----------------------------------------------------

Several cost variables can be set manually -- but usually shouldn't be
without extensive benchmarking. The defaults reveal the hardware model
PostgreSQL assumes:

.. list-table::
   :widths: 35 15 50
   :header-rows: 1
   :class: compact-table

   * - **Parameter**
     - **Default**
     - **Meaning**
   * - ``seq_page_cost``
     - 1.0
     - Cost of fetching a disk page in a sequential scan
   * - ``random_page_cost``
     - 4.0
     - Cost of fetching a non-sequentially-fetched disk page. Lower it
       to make index scans relatively cheaper; raise it to make them
       relatively more expensive.
   * - ``cpu_tuple_cost``
     - 0.01
     - Cost of processing each row during a query
   * - ``cpu_index_tuple_cost``
     - 0.005
     - Cost of processing each index entry during an index scan
   * - ``cpu_operator_cost``
     - 0.0025
     - Cost of processing each operator or function executed
   * - ``parallel_setup_cost``
     - 1000
     - Cost of launching parallel worker processes
   * - ``parallel_tuple_cost``
     - 0.1
     - Cost of transferring one tuple from a parallel worker to
       another process

Notice what the defaults imply:

- Disk pages are **4x more expensive** random vs sequential -- the
  model assumes spinning rust, not pure SSD. On SSD-only deployments,
  lowering ``random_page_cost`` often improves plan quality.
- Launching a parallel worker is **~1000 tuples' worth of CPU** -- so
  parallelism only pays on large queries.

PostgreSQL also gathers statistics continuously. The ``ANALYZE``
command (distinct from the ``EXPLAIN ANALYZE`` clause!) refreshes
those stats, and stale stats are a common cause of bad plans.


Magic Numbers for Computer Engineers
----------------------------------------------------

Useful context when reading cost numbers and designing schemas:

.. list-table::
   :widths: 50 50
   :header-rows: 1
   :class: compact-table

   * - **Operation**
     - **Approximate latency**
   * - L1 cache reference
     - 1 nanosecond
   * - L2 cache reference
     - 4 nanoseconds
   * - Main memory / RAM reference
     - 100 nanoseconds
   * - SSD random read
     - 16 microseconds
   * - Disk (hard drive / magnetic) seek
     - 3 milliseconds
   * - Read 1 MB sequentially from RAM
     - 4 microseconds
   * - Read 1 MB sequentially from SSD
     - 62 microseconds
   * - Read 1 MB sequentially from disk
     - 947 microseconds
   * - Round-trip network request in the same data center
     - 500 microseconds
   * - Send 2 KB over a commodity network
     - 62 nanoseconds

Two reads of the same row differ by **four orders of magnitude**
depending on whether the row is in L1 cache or on a spinning disk.
This is why cache hits and buffer management dominate query
performance at scale.


4 -- Advanced Query Plans: Inside Out
====================================================

Plans for complex queries are nested. You read them **inside-out** /
**bottom-up**: the deepest indented step runs first, and work bubbles
up to the top.


A Complex Query and Its Plan
----------------------------------------------------

.. code-block:: sql

   EXPLAIN ANALYZE
   SELECT departments.name,
          COUNT(employees.id)     AS total_employees,
          AVG(employees.salary)   AS average_salary
   FROM departments
   JOIN employees ON departments.name = employees.department
   WHERE employees.hire_date > '2020-01-01'
   GROUP BY departments.name
   HAVING COUNT(employees.id) > 10
   ORDER BY average_salary DESC
   LIMIT 5;

Plan (abridged):

.. code-block:: text

    Limit  (cost=312.29..312.30 rows=5 width=72) (actual time=3.606..3.608 rows=4 loops=1)
      ->  Sort  (cost=312.29..312.46 rows=67 width=72)
            Sort Key: (avg(employees.salary)) DESC
            Sort Method: quicksort  Memory: 25kB
            ->  GroupAggregate  (cost=160.44..311.18 rows=67 width=72)
                  Group Key: departments.name
                  Filter: (count(employees.id) > 10)
                  ->  Merge Join  (cost=160.44..260.60 rows=6344 width=40)
                        Merge Cond: ((employees.department)::text = (departments.name)::text)
                        ->  Sort  (cost=72.27..74.77 rows=999 width=15)
                              Sort Key: employees.department
                              Sort Method: quicksort  Memory: 60kB
                              ->  Seq Scan on employees  (cost=0.00..22.50 rows=999 width=15)
                                    Filter: (hire_date > '2020-01-01'::date)
                                    Rows Removed by Filter: 1
                        ->  Sort  (cost=88.17..91.35 rows=1270 width=32)
                              Sort Key: departments.name
                              Sort Method: quicksort  Memory: 25kB
                              ->  Seq Scan on departments  (cost=0.00..22.70 rows=1270 width=32)
    Planning Time: 0.314 ms
    Execution Time: 3.756 ms


Unwinding the Plan Step by Step
----------------------------------------------------

1. **Seq Scan on departments** -- the database sequentially scans the
   ``departments`` table (the innermost operation on one branch).
2. **Sort (departments.name) via quicksort** -- output is sorted by
   ``departments.name`` in preparation for a **Merge Join**.
   Note the substantial startup cost -- **preparing to join is
   expensive**.
3. **Seq Scan on employees** with a ``hire_date > '2020-01-01'``
   filter.
4. **Sort (employees.department) via quicksort** -- the employees side
   is sorted on the join column.
5. **Merge Join** -- the two sorted streams are merged on
   ``employees.department = departments.name`` (a text comparison).
6. **GroupAggregate** -- results are grouped by ``departments.name``,
   ``COUNT`` and ``AVG`` are computed, and ``HAVING`` is applied
   (filtering out groups with ``count(employees.id) <= 10``).
7. **Sort (avg(salary)) DESC** -- the few remaining rows are sorted by
   average salary, descending.
8. **Limit** -- finally, only the top 5 are returned.

.. admonition:: Reflection
   :class: hint

   - Note the **row carry-forward**: rows are not filtered until we
     have done most of the work. If you could push filters earlier,
     you would save real time.
   - Which step is the most expensive? What is its cost range, and why?
   - Could this have been accelerated with a different **JOIN type**?
   - What do you think about the ``JOIN`` condition on string equality?


Join Key Selection Matters
----------------------------------------------------

The query above joins on a **string column** (``departments.name`` =
``employees.department``). Switching to a proper foreign-key relation
changes the plan substantially:

.. code-block:: sql

   EXPLAIN ANALYZE
   SELECT departments.name,
          COUNT(employees.id)     AS total_employees,
          AVG(employees.salary)   AS average_salary
   FROM departments
   JOIN employees ON departments.id = employees.department_id
   WHERE employees.hire_date > '2020-01-01'
   GROUP BY departments.name
   HAVING COUNT(employees.id) > 10
   ORDER BY average_salary DESC
   LIMIT 5;

Abridged plan:

.. code-block:: text

    Limit  (cost=60.15..60.16 rows=5 width=72) (actual time=1.216..1.218 rows=4 loops=1)
      ->  Sort
            ->  HashAggregate
                  Group Key: departments.name
                  Filter: (count(employees.id) > 10)
                  ->  Nested Loop
                        ->  Seq Scan on employees
                              Filter: (hire_date > '2020-01-01'::date)
                        ->  Memoize
                              Cache Key: employees.department_id
                              Cache Mode: logical
                              Hits: 995  Misses: 4  Evictions: 0
                              ->  Index Scan using departments_pkey on departments
                                    Index Cond: (id = employees.department_id)
    Planning Time: 0.331 ms
    Execution Time: 1.308 ms

Same result, dramatically different plan:

- **Nested Loop + Index Scan + Memoize** replaces **Merge Join +
  double Sort**.
- **Memoize** is essentially a local cache over an index-only scan --
  995 cache hits, 4 misses out of 999 iterations.
- Execution time dropped from **3.756 ms** to **1.308 ms** -- nearly
  **3x** from a modeling improvement, not a code change.

The lesson: **small changes in data modeling and query construction
can have material impacts on performance**. Foreign-key columns
(integer, indexed) are dramatically cheaper join keys than unindexed
strings.


Debugging Complex Plans: CTEs, Views, Temp Tables
----------------------------------------------------

You will encounter queries that use **Common Table Expressions
(CTEs)**, **views**, or **temp tables**. If you just ``EXPLAIN`` them,
you may not see inside.

.. code-block:: sql

   EXPLAIN ANALYZE
   WITH JuniorEmployees AS (
       SELECT * FROM employees WHERE hire_date > '2022-01-01'
   )
   SELECT department_id, COUNT(*) AS total_junior_employees
   FROM JuniorEmployees
   GROUP BY department_id;

The plan shows the group-by on top of a ``Seq Scan on employees`` with
a filter, but **depending on the version and CTE form** the internal
SQL (``SELECT * FROM employees WHERE hire_date > '2022-01-01'``) may
be shown inlined, materialized, or partially optimized away.

Strategies:

- In modern PostgreSQL, simple (non-recursive, non-mutable) CTEs are
  **inlined** into the outer query by default.
- **Break CTEs and views into component queries** to profile them
  individually. Knowing the cost of each building block helps you
  reason about overall performance.
- Remember that CTEs and views have performance impacts of their own
  (materialization boundaries, repeated scans in older versions).


5 -- Advanced Analysis: SERIALIZE, MEMORY, BUFFERS
====================================================

``EXPLAIN ANALYZE`` alone shows only CPU-bound behavior. Additional
flags expose **IO**, **memory**, and **serialization** cost.


SERIALIZE -- Output Size and Format
----------------------------------------------------

.. code-block:: sql

   EXPLAIN (ANALYZE, SERIALIZE)
   SELECT * FROM employees WHERE age > 30;

.. code-block:: text

    Seq Scan on employees  (cost=0.00..22.50 rows=791 width=39) (actual time=0.062..0.282 rows=791 loops=1)
      Filter: (age > 30)
      Rows Removed by Filter: 209
    Planning Time: 0.167 ms
    Serialization: time=0.324 ms  output=55kB  format=text
    Execution Time: 0.756 ms

Adds a **Serialization** line showing how long it took to convert
results into a wire format, how much output was produced (55 kB), and
in what format. Useful when network transfer dominates query cost.


MEMORY -- Planner Memory Usage
----------------------------------------------------

.. code-block:: sql

   EXPLAIN (ANALYZE, MEMORY)
   SELECT * FROM employees WHERE age > 30;

.. code-block:: text

    Seq Scan on employees  (cost=0.00..22.50 rows=791 width=39) (actual time=0.049..0.219 rows=791 loops=1)
      Filter: (age > 30)
      Rows Removed by Filter: 209
    Planning:
      Memory: used=10kB  allocated=16kB
    Planning Time: 0.159 ms
    Execution Time: 0.279 ms

Shows how much memory the **planner** used. Useful when plan
generation itself becomes a bottleneck (very large schemas, complex
queries with many candidate plans).


BUFFERS -- IO Behavior
----------------------------------------------------

.. code-block:: sql

   EXPLAIN (ANALYZE, BUFFERS)
   SELECT * FROM employees WHERE age > 30;

.. code-block:: text

    Seq Scan on employees  (cost=0.00..22.50 rows=791 width=39) (actual time=0.019..0.199 rows=791 loops=1)
      Filter: (age > 30)
      Rows Removed by Filter: 209
      Buffers: shared hit=10
    Planning Time: 0.066 ms
    Execution Time: 0.263 ms

The ``Buffers: shared hit=10`` line tells you:

- **shared** -- the cache for table and index data (``shared_buffers``).
- **hit** -- data was found in the cache; **no disk read required**.
- **10** -- amount of data read in **buffers** (default PostgreSQL
  page size is 8 kB, so ~80 kB).

Had the data been on disk, you would see ``read=N`` annotations
instead.

.. admonition:: Key Insight
   :class: tip

   Use **BUFFERS** to improve **cold-cache** queries. A query that is
   fast on a warm cache but slow cold is a prime candidate for either
   more memory (``shared_buffers``) or a better index that reduces the
   number of pages touched.

Interpreting BUFFERS:

1. **Cache efficiency** -- if everything hits cache, IO is not your
   bottleneck.
2. **Hits vs reads** -- the query plan annotates ``read=N`` when data
   had to come from disk. Fix by giving the server more memory or
   redesigning table/index layout so the working set fits.


.. admonition:: Reflection
   :class: hint

   - For the complex query earlier, what is the largest impact to
     performance? Why?
   - How would a **BUFFERS** query help identify queries that could
     benefit from an index?


6 -- Improving Performance with Indexes
====================================================


When to Consider Indexes
----------------------------------------------------

Indexes help most when the query plan shows:

1. **Large or complex joins** -- joins often require substantial IO.
2. **Large aggregations** -- aggregations without indexes can be
   expensive.
3. **Complex sorting** -- large sorts can spill to disk, raising IO
   cost.
4. **Large table scans** -- large scans often read from disk, again
   raising IO.

``sort`` and ``group by`` operations are often **implicit** in a
query, and performing them "too soon" in the plan is a classic
footgun.


Fixes Before Indexes
----------------------------------------------------

Before adding an index, try the cheaper options first:

1. **Work with less data**: project fewer columns and filter early.
2. **Add indexes** -- but only where a real query benefits.
3. **Increase ``work_mem``**: lets more operations (sorts, hashes)
   stay in memory instead of spilling to disk.
4. **Increase ``shared_buffers``**: certain query patterns benefit
   from a larger table/index cache.


SARGABLE Queries
----------------------------------------------------

Not every slow query is an index problem. Indexes have real performance
and resource costs (write amplification, storage, maintenance), and
not all queries can even benefit from an index.

As a rule of thumb: for an index to help, the query must be
**SARGABLE** -- **S**\ earch **ARG**\ ument **ABLE**. A SARGABLE query
uses operators and functions that can take advantage of indexes, with
simple comparisons on columns and no transformations on the indexed
side.


SARGABLE Patterns
----------------------------------------------------

These are index-friendly:

- **Equality and inequality**: ``=``, ``>``, ``<``, ``!=``.
- **Ranges**: ``BETWEEN a AND b``.
- **Membership**: ``IN (...)``.
- **Comparisons that only evaluate the right side once**:
  ``salary > 100 * 10`` (the ``100 * 10`` is a constant).
- **Left-anchored LIKE**: ``LIKE 'ada%'`` -- works with B-tree indexes
  because the index tree can prefix-match.


Non-SARGABLE Anti-patterns
----------------------------------------------------

These defeat indexes on the column they touch:

- **Type conversions** on the indexed column -- often hidden by
  implicit casts.
- **Arithmetic on the column**: ``salary + 1 > 10`` forces a row-by-row
  evaluation.
- **Leading wildcards** in ``LIKE``: ``LIKE '%achary'`` or
  ``LIKE '%ity of Mar%'``.
- **Functions on the column** in ``WHERE``: ``UPPER(name) = 'ADA'``,
  ``LOWER(email)``, ``SUBSTRING(...)``. (A functional index on the
  expression can rescue this, but only if created deliberately.)
- **Negation operators** on indexed columns: ``NOT IN``, ``NOT LIKE``,
  ``NOT EXISTS`` -- these often force the planner to scan the whole
  range rather than jump to a specific index entry.


Deciding What to Index
----------------------------------------------------

Once you know a query is SARGABLE, the next decision is **which**
columns to index. Situational, but with guidelines:

- If the query plan shows a **large sequential scan**, an index will
  usually accelerate it.
- **Prioritize columns frequently used in ``WHERE`` clauses**.
- **Include columns commonly used in ``JOIN`` conditions**.
- **Consider columns used in ``ORDER BY`` and ``GROUP BY``** -- an
  index matching the order means no sort step.


Compound Indexes
----------------------------------------------------

- If two or more columns are often used together in a query, a
  **compound index** over them is usually better than two single-column
  indexes.
- **Order matters**. An index on ``(col1, col2)`` can serve queries
  filtering on ``col1`` alone, but **not ``col2`` alone**.
- The **leftmost-prefix rule**: on an index ``(col1, col2, col3)``,
  queries filtering on ``col1``, ``col1 + col2``, or all three benefit
  from the index. Other combinations do not.
- Be mindful of **redundancy** with existing indexes (e.g., don't keep
  both ``(a)`` and ``(a, b)`` if the compound covers the first).


Index Drawbacks
----------------------------------------------------

Indexes are not free:

- **Write performance**: ``INSERT`` / ``UPDATE`` / ``DELETE`` must
  maintain every relevant index. Write vs read performance is always
  a trade-off, especially with many or complex indexes.
- **Index size**: compound indexes use more memory and disk than
  single-column indexes, and both consume more space than an
  unindexed column. Less of a concern today than historically, but
  material for very large databases.


7 -- Join Strategies and Performance
====================================================

Finally, we come to ``JOIN``. This is large and challenging enough
that some teams advise structuring the database to avoid ``JOIN``
entirely. The NoSQL movement taught us that joins **cannot always be
avoided**, though -- so understanding the physical strategies matters.

PostgreSQL picks between three physical join algorithms: **nested
loop**, **merge join**, and **hash join**. Each has distinct
performance characteristics.


Nested Loop Join
----------------------------------------------------

- The simplest strategy: for every row in the **outer** relation, scan
  the **inner** relation looking for matches.
- **Slow for large tables**, but efficient when one side is very
  small.
- Indexing the **outer** relation is ineffective, but an **indexed
  inner** relation can produce dramatic speedups by reducing IO --
  this is how the Memoize / Index Scan variant earlier in the lecture
  got its performance.


Merge Join
----------------------------------------------------

- Operates against **equality** join conditions by sorting both
  tables on the join key, then iterating both sorted streams in
  parallel to find matching rows.
- A good strategy when a hash table would not fit in memory, but
  **not fast** -- the two sort steps are expensive.
- **Indexing the join keys** on both relations can accelerate the
  comparisons (the planner may skip the sort if the data is already
  in order).


Hash Join
----------------------------------------------------

- Build a **hash table** from the inner relation; then scan the outer
  relation and probe the hash table for each row.
- **Best when the hash table fits in memory** and the relations are
  not so tiny that iteration would beat table construction.
- There is no "quick" way to build an index for a hash join -- that is
  effectively what the hash join is doing on the fly.


How PostgreSQL Picks a Join Strategy
----------------------------------------------------

The planner picks a strategy per query based on:

- **Size of the data**: small tables → nested loop; larger tables →
  hash join; if even larger (too big to hash) → merge join.
- **Memory availability (``work_mem``)**: the smaller table must fit
  relative to ``work_mem`` for a hash join to be feasible.
- **Indexes**: availability and suitability of indexes significantly
  affect the choice. Indexed columns often lead to nested loop or
  merge joins.
- **Data distribution and selectivity**: the optimizer's row-count
  estimates change its cost model.
- **Join conditions**: equality vs non-equality matters -- merge join
  and hash join both require equality.


Summary
====================================================

Improving SQL database performance follows some high-level rules:

- **Examine query plans before optimizing**.
- Use appropriate **data types** and keep columns narrow.
- **Filter early** with ``WHERE``.
- Avoid unnecessary **sorting** and **grouping**.
- **Optimize join operations** -- pick join keys that play well with
  indexes, and understand which physical strategy the planner chose.
- **Limit result-set size** -- only return the rows and columns you
  need.
- **Use indexes appropriately** -- ensure queries are SARGABLE, design
  compound indexes around real workloads, and accept the write-cost
  trade-off.
